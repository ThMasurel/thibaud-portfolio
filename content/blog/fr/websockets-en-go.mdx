## WebSocket en deux mots

Un WebSocket, c'est une connexion persistante et bidirectionnelle entre le client et le serveur. Contrairement à HTTP où le client fait une requête et le serveur répond, ici la connexion reste ouverte. Le serveur peut envoyer des données au client quand il veut, sans que le client demande quoi que ce soit. Pour du chat, des notifications live ou de la synchro de données, c'est exactement ce qu'il faut.

## L'implémentation en Go

### gorilla/websocket

En Go, le package `gorilla/websocket` est incontournable. C'est lui qui gère l'upgrade de la connexion HTTP vers WebSocket :

```go
var upgrader = websocket.Upgrader{
    ReadBufferSize:  1024,
    WriteBufferSize: 1024,
    CheckOrigin: func(r *http.Request) bool {
        return true // En prod, on vérifie l'origine
    },
}
```

### Le pattern Hub

Le vrai sujet, c'est comment gérer des dizaines (ou des centaines) de connexions simultanées. La réponse : le pattern Hub. Un point central qui maintient la liste des clients connectés et route les messages.

```go
type Hub struct {
    clients    map[*Client]bool
    broadcast  chan []byte
    register   chan *Client
    unregister chan *Client
}
```

L'idée est simple : chaque nouvelle connexion s'enregistre auprès du Hub, chaque déconnexion se désenregistre, et les messages transitent par un channel central.

### La boucle principale

Le cœur de tout ça, c'est la méthode `Run()`. Elle tourne dans sa propre goroutine et utilise un `select` pour traiter les événements au fil de l'eau :

```go
func (h *Hub) Run() {
    for {
        select {
        case client := <-h.register:
            h.clients[client] = true
        case client := <-h.unregister:
            if _, ok := h.clients[client]; ok {
                delete(h.clients, client)
                close(client.send)
            }
        case message := <-h.broadcast:
            for client := range h.clients {
                select {
                case client.send <- message:
                default:
                    close(client.send)
                    delete(h.clients, client)
                }
            }
        }
    }
}
```

Le `default` dans le select intérieur est crucial : si un client ne consomme pas ses messages (connexion lente, crash côté navigateur), on le déconnecte plutôt que de bloquer tout le Hub. Sans ça, un seul client planté peut paralyser le serveur entier.

Chaque client a deux goroutines : une qui lit les messages entrants (`readPump`), une qui écrit les messages sortants (`writePump`). Le Hub orchestre le tout.

## Les pièges que j'ai rencontrés

### Les goroutines zombies

Le bug le plus vicieux que j'ai eu : la mémoire du serveur qui grimpait sans arrêt. Au bout de quelques heures de test, le process Go bouffait des centaines de Mo. La cause ? Des goroutines qui restaient bloquées sur un `send` vers un client déjà parti. Le channel n'était pas fermé proprement dans certains edge cases de déconnexion.

La leçon que j'en tire : toujours prévoir une condition de sortie claire pour chaque goroutine. Un `defer` qui ferme le channel, un timeout, un context — peu importe, mais il faut que la goroutine puisse mourir.

### Le ping/pong

Un WebSocket peut être "ouvert" côté serveur alors que le client a fermé l'onglet depuis 10 minutes. La seule façon de le savoir, c'est d'envoyer des pings réguliers et d'attendre le pong. Si le pong ne revient pas dans le délai imparti, on considère le client comme mort et on nettoie.

### Tester la concurrence

Les bugs de concurrence, c'est fourbe. Tout marche avec 2 utilisateurs connectés. Avec 20, le serveur panic sur un `concurrent map write`. Ça m'a appris à toujours tester en conditions réalistes — plusieurs onglets, des connexions/déconnexions rapides, des messages envoyés en rafale.

## Ce que je retiens

Les WebSockets en Go, c'est puissant. Les goroutines et les channels sont faits pour ça — gérer de la concurrence sans se prendre la tête avec des threads et des mutexes partout. Mais ça demande de la rigueur : chaque goroutine doit avoir une fin, chaque channel doit être fermé, et chaque cas d'erreur doit être anticipé.

Avoir exploré tout ça par curiosité sur TeamUp Hub avant de le retrouver en formation, ça m'a donné un vrai avantage. C'est aussi ça, apprendre à coder : les side projects nourrissent la formation, et la formation structure les side projects.
