## How I got into this

While working on TeamUp Hub, my personal project built with React and Node.js, I needed real-time notifications. Rather than polling every 5 seconds like it's 2010, I dove into WebSockets. I spent quite a few evenings wrapping my head around the protocol, testing implementations, and breaking things along the way.

The timing turned out to be perfect: a few weeks later, my school curriculum asked me to build a real-time forum in Go with private chat over WebSocket. I already had the concepts down — I just had to translate them into Go. It's one of those moments where personal curiosity pays off. I was the only one in my group who didn't start from scratch on the topic.

## WebSocket in a nutshell

A WebSocket is a persistent, bidirectional connection between client and server. Unlike HTTP where the client makes a request and the server responds, here the connection stays open. The server can push data to the client whenever it wants, without the client asking for anything. For chat, live notifications, or data synchronization, it's exactly the right tool.

## Implementing it in Go

### gorilla/websocket

In Go, the `gorilla/websocket` package is the go-to choice. It handles the upgrade from an HTTP connection to a WebSocket:

```go
var upgrader = websocket.Upgrader{
    ReadBufferSize:  1024,
    WriteBufferSize: 1024,
    CheckOrigin: func(r *http.Request) bool {
        return true // In production, check the origin
    },
}
```

### The Hub pattern

The real challenge is managing dozens (or hundreds) of simultaneous connections. The answer: the Hub pattern. A central point that keeps track of connected clients and routes messages between them.

```go
type Hub struct {
    clients    map[*Client]bool
    broadcast  chan []byte
    register   chan *Client
    unregister chan *Client
}
```

The idea is straightforward: every new connection registers with the Hub, every disconnection unregisters, and messages flow through a central channel.

### The main loop

The heart of the whole thing is the `Run()` method. It runs in its own goroutine and uses a `select` to process events as they come:

```go
func (h *Hub) Run() {
    for {
        select {
        case client := <-h.register:
            h.clients[client] = true
        case client := <-h.unregister:
            if _, ok := h.clients[client]; ok {
                delete(h.clients, client)
                close(client.send)
            }
        case message := <-h.broadcast:
            for client := range h.clients {
                select {
                case client.send <- message:
                default:
                    close(client.send)
                    delete(h.clients, client)
                }
            }
        }
    }
}
```

That `default` in the inner select is crucial: if a client isn't consuming its messages (slow connection, browser crash), we disconnect it rather than blocking the entire Hub. Without it, a single stalled client can freeze the whole server.

Each client runs two goroutines: one reading incoming messages (`readPump`), one writing outgoing messages (`writePump`). The Hub orchestrates everything.

## The traps I fell into

### Zombie goroutines

The nastiest bug I had: the server's memory climbing non-stop. After a few hours of testing, the Go process was eating up hundreds of megabytes. The cause? Goroutines stuck waiting to send to a client that was already gone. The channel wasn't being closed properly in certain edge cases during disconnection.

The takeaway: always have a clear exit path for every goroutine. A `defer` that closes the channel, a timeout, a context — whatever works, but the goroutine needs to be able to die.

### Ping/pong

A WebSocket can be "open" server-side while the client closed the tab 10 minutes ago. The only way to know is to send regular pings and wait for the pong. If the pong doesn't come back in time, the client is considered dead and we clean up.

### Testing concurrency

Concurrency bugs are sneaky. Everything works fine with 2 connected users. With 20, the server panics on a `concurrent map write`. That taught me to always test under realistic conditions — multiple tabs, rapid connect/disconnect cycles, messages sent in bursts.

## What I take away from this

WebSockets in Go are powerful. Goroutines and channels were made for this — handling concurrency without getting bogged down in threads and mutexes. But it demands discipline: every goroutine must have an end, every channel must be closed, and every error case must be anticipated.

Having explored all of this out of curiosity on TeamUp Hub before encountering it in my coursework gave me a real edge. That's the thing about learning to code: side projects feed into your formal training, and formal training gives structure to your side projects.
