## Le déclic

Mon ancien portfolio, c'était un site HTML/CSS tout bête hébergé sur GitHub Pages. Il faisait le job, mais à chaque fois que je voulais ajouter un projet ou écrire un article, il fallait tout coder à la main. J'en avais marre. Je voulais un truc propre, avec un blog intégré, du bilingue, et surtout quelque chose dont je sois fier.

## Pourquoi cette stack ?

### Next.js App Router

J'avais déjà bossé avec React sur TeamUp Hub, donc Next.js était la suite logique. L'App Router m'a séduit : le routing est basé sur l'arborescence de fichiers, le rendu serveur est natif, et le déploiement sur Vercel se fait en un push. Franchement, une fois qu'on y goûte, on ne revient pas en arrière.

### Tailwind CSS et le glassmorphism

Tailwind, c'est le genre d'outil où au début on se dit "pourquoi j'écrirais mes classes dans le HTML ?" et deux jours plus tard on ne peut plus s'en passer. Pour le design, j'ai joué avec `backdrop-blur` et des bordures semi-transparentes pour donner cet effet vitré. C'est subtil mais ça change tout l'aspect du site.

### Velite pour le blog

J'ai d'abord regardé Contentlayer, sauf que le projet est abandonné depuis un moment. Du coup je me suis tourné vers Velite : des schémas Zod pour valider les métadonnées de chaque article, du MDX natif, et une intégration propre avec Next.js. Chaque article est un fichier `.mdx` et tout est typé de bout en bout — si je me trompe dans le frontmatter, le build me le dit tout de suite.

### next-intl pour le bilingue

Le support FR/EN était non négociable. Je voulais un portfolio accessible aussi bien à un recruteur parisien qu'à une boîte internationale. `next-intl` s'intègre parfaitement avec l'App Router : les traductions sont chargées côté serveur et disponibles partout via `useTranslations`. Zéro flash, zéro galère.

## L'architecture

Rien de révolutionnaire, mais c'est solide :
- `[locale]/` pour gérer le routing i18n automatiquement
- Des composants serveur par défaut, du client uniquement là où c'est nécessaire (animations, toggles)
- Le blog passe par Velite qui transforme les fichiers MDX en données typées au build

## Les galères (et ce que j'en retiens)

### Le "use client" partout

Au début, j'ai fait l'erreur classique : coller `"use client"` sur quasi tous mes composants. Résultat : un bundle JS bien trop gros et des perfs médiocres. J'ai appris à garder les composants serveur au maximum et à isoler l'interactivité dans des wrappers clients minimalistes.

### Le flash du dark mode

Premier chargement en dark mode : flash blanc pendant 200ms. Horrible. La solution, c'est un script inline dans le `<head>` qui applique la classe `dark` avant même que React se charge :

```javascript
(function() {
  try {
    var theme = localStorage.getItem('theme');
    if (theme === 'dark' || (!theme && window.matchMedia('(prefers-color-scheme: dark)').matches)) {
      document.documentElement.classList.add('dark');
    }
  } catch(e) {}
})();
```

Ça a l'air de rien, mais ça m'a pris un bon moment à comprendre pourquoi le flash persistait même avec un `useEffect`. Le problème c'est que React s'hydrate après le premier paint du navigateur — d'où l'intérêt du script bloquant dans le head.

### Les animations au bon moment

J'ai arrêté de tout animer au chargement de la page. `whileInView` de motion, c'est la bonne approche : les éléments s'animent quand l'utilisateur scrolle jusqu'à eux. C'est plus naturel et ça évite les animations que personne ne voit parce qu'elles se jouent hors écran.

## Conclusion

Ce portfolio m'a autant appris que mes projets de formation. C'est le genre de side project où on touche à tout : design, archi, perf, i18n, déploiement. Le code source est sur GitHub si ça vous intéresse — n'hésitez pas à fouiller.
